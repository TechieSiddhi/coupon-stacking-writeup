Two checks, one truth they forgot to share

A coupon endpoint is really two functions wearing one route: "is this code real?" and "have I already used it?" Both are supposed to agree on what a code is. Here they didn't — and the gap between them was exactly one whitespace character wide, twice over, which was all it took to turn a capped 50% discount into a free checkout.

The Setup

A minimal storefront, one hero item: the Midnight Collection at €666.00. Every visitor is dropped in with €66.00 of credit — a tenth of the price, a deliberate signal that the challenge is about discounts, not balance.

Two coupons exist. NIGHT20 sits in plain sight in the site banner. NEWS30 takes one extra step — submit any email to POST /api/newsletter and it comes back in the response. Both apply through POST /api/cart/coupon, and the app's own math caps a combined application of both at 50% off. Getting to zero means finding a way past that cap.

Where the Two Checks Disagree

Tracing /api/cart/coupon's handling of the code field turns up two separate questions it answers, using two different versions of the same input:

  • "Is it real?" — answered against a trimmed copy of the code.
  • "Have I seen it before?" — answered against the raw, un-trimmed code.

Feed it "NIGHT20 " (one trailing space) and the first check says yes, that's NIGHT20, 20% off is real. The second check compares the literal string against what's already been recorded, sees a string it's never stored before, and says no, this isn't a repeat. Testing further variants (double spaces, leading spaces, tabs) showed the same gap holds for each — but only once per variant tried; it isn't an unlimited stack, it's exactly one extra application per distinct way of writing the code.

Why This Isn't Just a Curiosity

The practical ceiling here — exactly double, not unlimited — comes from this specific store having exactly two coupons and a 50% combined cap. The underlying bug has no such ceiling: it's a property of how the dedup check compares strings, not of how many coupons exist. Add a third promo code to a real store running this logic, or let the discount math exceed 100% by accident, and the same whitespace trick keeps paying out past free into negative-price territory. The fix has to close the string-comparison gap itself, not just the two-coupon math that happens to cap it here.

Closing the Gap

01
Normalize before either check runs, and reuse that exact value

Trim and lowercase the code once, at the top of the handler, and let both the validity check and the dedup check read from that single normalized variable — never the original input again.

const normalized = code.trim().toUpperCase();

if (!KNOWN_CODES.has(normalized))
  throw 'Invalid coupon';

if (appliedCodes.has(normalized))
  throw 'Coupon already applied';

appliedCodes.add(normalized);
02
Make the stacking limit a real, server-side number

A Set only answers "have I seen this exact key before" — it isn't a stacking policy. If any code is meant to apply more than once, say so explicitly with a counted limit, not an implicit side effect of how the dedup check happens to compare values.

const MAX_USES_PER_CODE = 1;
const uses = appliedCodes.get(normalized) ?? 0;
if (uses >= MAX_USES_PER_CODE)
  throw 'Coupon already applied';
appliedCodes.set(normalized, uses + 1);
Fix 1 removes the discrepancy entirely. Fix 2 is the belt-and-suspenders version — it turns "how many times can this apply" from an accident of string comparison into a number someone actually chose.
